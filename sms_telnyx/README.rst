Send and receive SMS through `Telnyx <https://telnyx.com>`__.

Odoo 19 and 20 ship ``sms_twilio``, which makes the SMS provider a
per-company choice but offers only Odoo IAP and Twilio. This module adds
Telnyx as a third option and, unlike either of the built-ins, also
handles **inbound** messages:

- **Outbound** — ``sms.sms`` for a company set to Telnyx is sent through
  ``POST /v2/messages``, with delivery receipts reconciled back onto the
  ``sms.tracker``.
- **Inbound** — one webhook endpoint receives ``message.received``
  events, verifies Telnyx's Ed25519 signature, matches the sender to a
  partner and posts the text on that record's chatter, so a reply
  reaches the system of record instead of someone's handset.
- **Consent** — carrier-mandated ``STOP`` / ``START`` keywords add to
  and remove from ``phone.blacklist``, which core SMS sending already
  honours. Telnyx answers the sender on our behalf; suppressing our own
  sending is the part that is legally ours, and this is it.

Inbound routing is designed to be extended:
``sms.telnyx.inbound._route_target()`` returns the record to post on,
defaulting to the matched partner. A deployment with a helpdesk, a lease
or a reservation model should override it.

Configuration
=============

In Telnyx
---------

1. Create a **Messaging Profile** and buy at least one phone number,
   then assign the number to that profile. Sending from a number that is
   not on a profile fails with Telnyx error ``40300``.
2. For US traffic, complete **A2P 10DLC** brand and campaign
   registration. Unregistered messages to US numbers are blocked by the
   carriers, not by Telnyx, so this cannot be worked around and takes
   weeks — start it first.
3. Set the profile's **webhook URL** to
   ``https://<your-odoo>/sms_telnyx/webhook`` and the **webhook API
   version to v2**. v1 does not send an Ed25519 signature, so every
   delivery would be rejected.
4. Copy the **API key** (Account → Keys & Credentials) and the account's
   **public key** from the same page.

In Odoo
-------

Settings → General Settings → SMS:

1. Set **SMS Provider** to *Send via Telnyx*.
2. Click **Configure Telnyx Account** to open the account modal. Enter
   the API key, public key and messaging profile id, then add each DID
   with its country. The country matters twice: it selects the sending
   number for a given destination, and the number is how an inbound
   message is attributed to a company.

The public key is what makes the webhook trustworthy, so the endpoint
rejects everything while it is unset — including genuine Telnyx
deliveries. That is deliberate: an unauthenticated public route that
accepted anything would let a stranger file messages against your
customers.

Use **Send test SMS** with a test recipient to check the selected Telnyx
account. The test uses Telnyx even before the provider choice in
Settings is saved. **Update Account** closes the modal; save Settings to
apply the provider choice. The modal also shows the webhook URL to copy
into the Telnyx messaging profile.

Usage
=====

Sending is unchanged from stock Odoo: use the SMS composer from any
chatter, an SMS template, or a mass mailing. Which provider carries the
message is decided per company, so one database can have one entity on
Telnyx and another on Twilio.

Inbound messages appear as an ``sms`` message on the matched record's
chatter, authored by the contact, which notifies that record's
followers.

Every inbound message is also recorded in **Settings → Technical →
Inbound Telnyx Messages** (``sms.telnyx.inbound``) with the routing
decision:

+--------------------------+-------------------------------------------+
| State                    | Meaning                                   |
+==========================+===========================================+
| ``posted``               | Matched a partner and was filed on a      |
|                          | record                                    |
+--------------------------+-------------------------------------------+
| ``unmatched``            | No partner has this number — the text is  |
|                          | kept, not discarded                       |
+--------------------------+-------------------------------------------+
| ``opt_out`` / ``opt_in`` | A ``STOP`` / ``START`` keyword, applied   |
|                          | to ``phone.blacklist``                    |
+--------------------------+-------------------------------------------+
| ``pending``              | Recorded but not yet processed            |
+--------------------------+-------------------------------------------+

``unmatched`` is worth a periodic look: it is usually a contact whose
number was never captured, and it is the one case where a real message
reaches nobody.

Known issues / Roadmap
======================

- MMS is not handled. Inbound ``media`` is ignored and nothing is
  attached to the chatter message.
- Group messages (several entries in the inbound ``to`` array) take the
  first recipient only.
- Delivery failures are recorded with the core ``unknown`` failure type
  plus Telnyx's own text in the failure reason, rather than a mapped
  per-code failure type. Mapping them would mean extending the
  ``failure_type`` selection on both ``sms.sms`` and
  ``mail.notification``, which was judged not worth the collision risk
  for the information gained.
- Inbound processing is synchronous, because Telnyx expects a 2xx within
  two seconds and this module assumes no job queue. A deployment with
  ``queue_job`` installed would be better served deferring
  ``_process()``.
- The webhook tries every configured public key in turn. That is fine
  for a few companies and would want a per-company endpoint path at a
  few dozen.
